# 하네스 규약

이 문서는 Uni Translator 작업 완료 전에 실행하는 검증 하네스의 계약을 정의한다. 하네스의 진입점은
`.codex/hooks.json`의 `Stop` 훅이며, 실제 실행기는 `.codex/hooks/stop-verify.mjs`다. 명령 구성의 정본은
루트 `package.json`의 `scripts` 필드다.

## 적용 범위

- 소스 코드, 설정, 문서 등 저장소의 프로젝트 파일을 수정한 모든 작업에 적용한다.
- 읽기 전용 조사처럼 프로젝트 파일을 수정하지 않은 작업에는 실행을 요구하지 않는다.
- 특정 패키지만 수정했더라도 완료 게이트는 저장소 루트의 전체 워크스페이스를 대상으로 한다.
- 패키지별 집중 테스트는 개발 중 피드백을 줄이는 보조 수단이며, 이 완료 게이트를 대체하지 않는다.

## 사전 조건

1. 저장소 루트에서 `package.json`이 지정한 버전의 pnpm을 사용할 수 있어야 한다.
2. 워크스페이스 의존성이 설치되어 있어야 한다.
3. 사용자 또는 다른 도구가 만든 변경을 포함한 현재 작업 트리를 보존해야 한다. 하네스 통과를 위해 관련
   없는 변경을 되돌리거나 삭제하지 않는다.
4. 하네스 실행 전에 다음 사항을 사람이 검토한다.
    - 변경된 동작과 관련 문서가 서로 모순되지 않는가
    - 새 규칙이나 사용법이 권위 문서와 문서 지도에 반영되었는가
    - 수정한 코드의 역할과 호출 맥락을 설명할 수 있는가

## 고정 실행 순서

Stop 훅은 저장소 루트에서 다음 스크립트를 순서대로 실행한다.

| 순서 | 명령              | 계약                                                                                  |
| ---- | ----------------- | ------------------------------------------------------------------------------------- |
| 1    | `pnpm run format` | Prettier로 워크스페이스 파일을 자동 포맷한다. 파일이 바뀔 수 있다.                    |
| 2    | `pnpm run verify` | 아래 네 게이트를 순서대로 실행한다. 앞 게이트가 실패하면 뒤 게이트는 실행하지 않는다. |

현재 `verify`의 세부 순서는 다음과 같다.

1. `pnpm run format:check`: 포맷 결과가 안정적인지 확인한다.
2. `pnpm run lint`: OXLint로 워크스페이스를 검사한다.
3. `pnpm run test`: 각 워크스페이스 패키지의 존재하는 테스트를 실행한다.
4. `pnpm run build`: 각 워크스페이스 패키지의 존재하는 프로덕션 빌드를 실행한다.

`format`이 성공한 뒤에는 자동 수정된 파일도 작업 결과에 포함되므로 diff를 다시 검토한다. 검토 후 파일을
추가로 수정했다면 완료 전에 Stop 훅을 다시 실행한다.

## 훅 입출력 계약

- Codex는 Stop 이벤트의 JSON payload를 표준 입력으로 실행기에 전달한다.
- `stop_hook_active`가 참이면 실행기는 재귀적인 Stop 훅 실행을 막기 위해 검증을 다시 시작하지 않고 빈 JSON
  객체를 반환한다.
- 일반 실행에서는 각 명령의 표준 출력과 표준 오류를 훅 로그로 전달한다.
- 두 스크립트가 모두 종료 코드 `0`으로 끝나면 빈 JSON 객체를 반환하며 완료를 허용한다.
- 명령 실행 오류 또는 `0`이 아닌 종료 코드가 발생하면 실행기는 `decision: "block"`과 실패한 스크립트가
  포함된 이유를 반환한다. 이 경우 작업은 완료 상태가 아니다.
- `.codex/hooks.json`은 Stop 훅 제한 시간을 600초로 둔다. 호스트가 제한 시간 초과나 비정상 종료를 보고하면
  성공으로 간주하지 않는다.

POSIX와 Windows는 각각 `.codex/hooks.json`의 `command`와 `commandWindows`를 사용하지만, 둘 다 Git이
판별한 저장소 루트의 동일한 `stop-verify.mjs`를 실행해야 한다.

## 표준 작업 절차

1. 구현 또는 문서 수정을 마친다.
2. 문서 정합성, 반영 범위, 코드 역할과 맥락을 검토한다.
3. 필요한 집중 테스트를 실행하고 문제를 수정한다.
4. 완료를 요청해 `.codex/hooks.json`의 Stop 훅을 실행한다.
5. 훅이 만든 포맷 변경과 전체 로그를 검토한다.
6. 실패를 수정하거나 포맷 후 추가 변경이 생기면 Stop 훅을 다시 실행한다.
7. 마지막 Stop 훅이 성공한 경우에만 완료로 보고한다.

로컬 진단이 필요하면 저장소 루트에서 `pnpm run format`과 `pnpm run verify`를 같은 순서로 직접 실행할 수
있다. 직접 실행 결과는 문제를 미리 찾기 위한 것이며, 프로젝트 파일 수정 작업의 최종 Stop 훅 통과를
대체하지 않는다.

## 판정과 보고

완료 조건은 마지막 프로젝트 파일 수정 이후 실행된 Stop 훅에서 `format`과 `verify`가 모두 성공한 것이다.
최종 응답에는 다음을 명시한다.

- Stop 훅 실행 여부와 결과
- `format:check`, `lint`, `test`, `build`의 결과
- 남은 실패, 실행되지 않은 게이트, 환경 제약
- 하네스가 자동으로 수정한 파일이 있다면 그 사실

재현 가능한 실패가 남아 있으면 완료했다고 표현하지 않는다. 실패한 명령, 핵심 오류, 실행되지 않은 후속
게이트를 구체적으로 보고한다. 의존성이나 도구 부재처럼 환경 문제라면 확인한 상태와 미검증 범위를
구분한다.

## 계약 변경

하네스 명령이나 순서를 바꿀 때는 `.codex/hooks.json`, `.codex/hooks/stop-verify.mjs`, 루트
`package.json`, `AGENTS.md`, 이 문서를 함께 검토한다. 어느 한 파일만 바꿔 문서와 실행 동작이 달라지게
하지 않는다. 변경 후에는 성공 경로뿐 아니라 의도적인 실패가 `decision: "block"`을 반환하는지도
검증한다.
